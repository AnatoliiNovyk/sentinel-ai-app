# Batch 219: Retry/Backoff для доставки scan-result

## Як було
- Відправка результатів агента в `scan-result` виконувалась одним запитом без повторних спроб.
- За тимчасових мережевих/інфраструктурних помилок могла втрачатися доставка payload.
- Лог `Results reported` писався навіть коли доставка фактично падала.

## Що зроблено
- У `sentinel-agent/src/index.ts` додано retry/backoff для `reportResult`:
  - до 4 спроб;
  - exponential backoff (1s, 2s, 4s);
  - ретраї тільки для transient-помилок (`429`, `5xx`, `ECONNABORTED`, `ECONNRESET`, `ETIMEDOUT`, `ENOTFOUND`, `EAI_AGAIN`).
- Додано таймаут HTTP-виклику `scan-result` (`15000ms`).
- Додано діагностичні warn/error-логи для кожної невдалої спроби та фінального фейлу.
- Оновлено `runJob`, щоб success-log доставки писався тільки при реальному успіху `reportResult`.
- Для crash-path додано окремий лог, якщо навіть failure-payload не доставлено після всіх retry.
- Оновлено `EXECUTION_CHECKLIST_2026-04-28.md`: підпункт P1.1 позначено виконаним.

## Що покращило
- Зменшено ризик втрати результатів скану через короткочасні збої мережі/edge.
- Підвищено достовірність operational-логів (успіх/помилка доставки тепер відповідає факту).
- Підготовлено основу для наступних P1 кроків (audit trail та alerting).
